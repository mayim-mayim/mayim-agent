# mAG Activity Map API v1

The machine contract is [OpenAPI](../agent-api-schemas/mag-activity-map.openapi.json); closed DTOs are in [the JSON schema](../agent-api-schemas/mag-activity-map.v1.schema.json). The fixed implementation oracle is Charter `2577fd74cbdf8a40e0a1172f188fd021fd71f9fe`. This API does not change Task rewards, refunds, answer evaluation, APS/Template delivery or ritual services.

`GET /api/agent/activity-map/v1/manifest` discovers a verified generation. Public reads are `summary`, `agents`, `sites`, `relations`, `activities`, and `/{kind}/{public_id}`. Use `generation`, `period=today|7d|30d` (default `7d`), comma-separated `types`, case-insensitive substring `q`, and the opaque `cursor` returned by the same conditions. A page may contain no items and still have a continuation. Never convert unknown totals or incomplete source coverage to zero. The source receipt UTC instant determines the JST calendar window and stable ordering. Query matches public wallet addresses and permitted site names/hosts; matches are unioned. Free answers and private source attributes are not searched.

Initial lists contain minimum activity and node data. Fetch Activity detail only when selected. Entity detail is a bounded history page under the same conditions. `relation_scope` distinguishes `none_in_condition`, `obtained_unshown`, and `unknown`; the client separately knows which obtained partners it currently displays. A missing body is `body_state=unavailable`, not an empty answer. `409 generation_changed` requires a new manifest and discarding the old cursor, counts and detail while retaining the user's search/filter/layout choices. `409 cursor_mismatch` forbids cursor reuse under another condition. `503` is unavailable or not yet generated, never a completed empty graph. Public reads do not extend an old generation's JST window; an already-paid purchase has its own fixed window until its absolute expiry.

## Saved Task conditions

At the explicit operational start C, new condition fixation uses `activity_map_policy_id=mag.activity-map.public.v1` and the active `activity_map_epoch`. The date of approval, response or publication never defines C. Existing saved registration operations, quotes, uncertain results and Tasks keep their original signed bytes, digest and conditions. New Tasks made from existing Templates after C use the new contract. `GET` economic-offer responses use v2 with a separate `registration_contract` when C is active; economic amounts and revisions remain separate.

Paths are relative to `/agent-task-specs/`. The Choice pack also contains Catalog template registration v5 and task registration v4 schemas. Requester and Agent must see the pack's public conditions before registration signing, Claim and Paid external purchase. No additional signature ceremony is required. The accepted reward namespace and 20-byte address can join public activity across Tasks. Minimum history remains privately retained while the service exists, whereas this map exposes at most 30 JST calendar days. Minimum history excludes answer text, reasons, private execution IDs, tokens, IPs and raw payloads. Corrections, source stops and designated deletion still apply.

Choice, Template and generic Structured answers contribute independent history without URL-derived relationships. Visits, Paid reports and research use only source-confirmed relationships; a payment record does not assert successful use. PROFILE remains limited sharing. Hidden APS B contributes no public nodes, counts, order or search postings. A stop within one order does not change another order's owner authority.

## Purchase and recovery

Before any payment, atomically save a private client journal containing an independently random 128-bit `operation_id` (32 lowercase hex characters) and an independent 256-bit recovery secret (64 lowercase hex characters), selected generation, manifest hash and period `30d`. Do not log the secret or place it in a URL. Every purchase/control request uses `Authorization: MAG-Recovery <secret>`. Self-reported `agentId` is not buyer authentication.

1. POST `/purchases` under the API prefix with `operation_id`, `generation`, `manifest_sha256`, `period:"30d"`, and optional selected `scheme`, `asset`, `agentId`. The server saves this binding before external settlement. An initial 402 includes the same purchase fields and the existing rail challenge. A repeated identical initial request retrieves its saved challenge. Preserve the request; do not add payment proof fields to its JSON.
2. Complete the selected existing rail once. Preserve its complete authenticated payment reference/proof in the private journal. L402/MPP use `X-MAG-Payment-Authorization` for the original payment Authorization value. x402 uses `Payment-Signature`; legacy `paymentAuth` and Grant `paymentOverride` JSON use base64url UTF-8 in `X-MAG-Payment-Auth` and `X-MAG-Payment-Override`. The recovery Authorization stays separate. No Faucet or Graph refund route is added.
3. POST `/purchases/recover` with only `operation_id`, recovery Authorization and any original payment proof. Unknown settlement returns 202 `payment_unconfirmed`; it does not create a new payment challenge or instruct a second payment. A verified complete rail/network/asset/reference binds to one operation/request/manifest. Existing Grant consumption and the purchase commit share the existing Grant transaction.
4. GET `/purchases/{id}` for status. When `ACQUIRING`, GET its `/manifest` and `/parts/{part_id}`. All responses are `private, no-store`. Control and payload requests bypass additional paid quota purchases; ordinary non-charging 429 limits remain. A part request performs no settlement, Grant consumption, Task DB read, AI, Neo4j query, generation or progress write.
5. Verify the manifest's exact uncompressed UTF-8 bytes against the selected `manifest_sha256`. Its `parts_format=one-level-catalog`: `parts` lists immutable catalog pages with byte length and SHA-256. Fetch and verify those catalog pages; each `mag.activity-map.part-catalog.v1` contains the complete descriptors for its payload/index/detail parts. Catalog pages do not recurse. Deduplicate identical part IDs, verify and durably save every listed part. Hash received bytes, not reserialized JSON. Use one temporary file per part and atomic rename; keep the journal private.
6. Only after every catalog and payload part is verified and durable, POST `/purchases/{id}/complete` with `generation` and `manifest_sha256`. Complete is idempotent, but no new payload access follows `COMPLETE`. If only the complete response is lost, query status or resend the same complete notification; do not download or pay again.

`confirmed_at + 24 hours` is absolute and includes complete. Retry, midnight, credential presentation and replacement never extend it. `PAYMENT_PENDING`, `ACQUIRING`, `REPLACEMENT_REQUIRED`, `COMPLETE`, `UNAVAILABLE` and `EXPIRED_UNCONFIRMED` have distinct meanings. Expiry does not assert that nothing was received or that payment failed. Completed purchases remain complete after later expiry or source stop. Authentication failures are not converted into `UNAVAILABLE`.

A stopped generation cannot authorize a new request even on a Worker cache HIT. A compatible already-generated replacement, if present, is explicit: POST `/purchases/{id}/replacement` with old `generation`, `decision:"accept"`, `replacement_generation` and candidate `manifest_sha256`; or `decision:"decline"`. A replacement retains the original window/cutoff/schema/policy, adds no Activity and keeps the same expiry. Use a separate generation output directory; never mix parts or cursors. A safe candidate is not guaranteed. Absence or decline ends as `UNAVAILABLE` with its reason and preserved payment state.

Use initial attempt plus at most two retries per request, concurrency two for parts, connect timeout 10 seconds, read-inactivity timeout 60 seconds, 1/2-second exponential delays plus jitter. Honor `Retry-After`; never retry past purchase expiry. Stop finite retries and retain a resumable journal. Do not poll continuously or blindly retry 401, condition mismatch or terminal states. mAG Agent SDK (`mayim-agent` 2.0.0, import `mayim_agent`, class `MagClient`) must implement these client responsibilities; its source acceptance is separate.

## Retired and retained services

Dedicated Benchmark, Sandbox/Interop, Metrics/Trust, independent domain/sponsor/track, preflight/Goal/trace and old single-Graph routes return HTTP 410 with `error_code=service_retired`, `retryable=false`, `actions=[]`, before billing. The old Graph never redirects to this API or returns its new DTO as an old 200. External observe/observations, Failure observe/observations/options/search, External summary/domains/latest, Task domain-observation ingress/retry, shared paid-results, Guide/logs/Confession and GishikiGraphSync/GetGraph/Oracle remain. Method and purpose determine retirement; `monzen/register`, report-sinner and blacklist are not retired by prefix.
